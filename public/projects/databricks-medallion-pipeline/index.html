Databricks Medallion Pipeline

The SQL Server warehouse proved the data model. Here the same CRM and ERP integration runs on Databricks: raw files in a Unity Catalog volume, transformations in PySpark and tables in Delta Lake.

Source code on GitHub ↗

Architecture

Everything lives in one Unity Catalog, datalakehouse, and runs as four dependent stages.

  1. 1init_lakehouseSchemas and source volume
  2. 2bronzeSix CSVs into Delta tables
  3. 3silver_orchestrationSix PySpark cleaning notebooks
  4. 4gold_orchestrationDimensions first, then fact_sales

What I built

  1. Set up the catalog

    Created bronze, silver and gold schemas and a volume for the raw files.

  2. Clean in PySpark

    Six Silver notebooks trim every string column automatically, parse dates, and conform keys and codes.

  3. Model in order

    Gold builds both dimensions with surrogate keys first, then loads fact_sales.

Results

6 Bronze tables→6 Silver tables→3 Gold tables

A star schema in Delta Lake that answers questions like revenue by country and product line:

SELECT c.country, p.product_line, SUM(f.sales_amount) AS total_sales
FROM   datalakehouse.gold.fact_sales f
JOIN   datalakehouse.gold.dim_customers c ON f.customer_key = c.customer_key
JOIN   datalakehouse.gold.dim_products  p ON f.product_key  = p.product_key
GROUP  BY c.country, p.product_line
ORDER  BY total_sales DESC;

Evidence and technical details

Architecture

Everything lives in a Unity Catalog called datalakehouse, with one schema per layer and a volume for the raw files:

  • init_lakehouse creates the bronze, silver and gold schemas and the datalakehouse.bronze.source_systems volume.
  • Bronze reads each CSV with headers and schema inference and overwrites a managed Delta table.
  • Silver is driven by silver_orchestration, which runs six child notebooks with dbutils.notebook.run.
  • Gold is driven by gold_orchestration, which builds the dimensions first and the fact table last, in dependency order.
Silver transformations
Silver tableFrom BronzeKey transformations
crm_customerscrm_cust_infoTrim strings; normalize marital status and gender; drop null IDs; rename columns.
crm_productscrm_prd_infoParse the product key; default null cost; normalize product line; cast the start date.
crm_salescrm_sales_detailsParse yyyyMMdd dates; derive price from sales ÷ quantity when invalid.
erp_customerserp_cust_az12Strip the NAS prefix; validate birth dates; normalize gender.
erp_customer_locationerp_loc_a101Clean customer IDs; map country codes (DE, US, …).
erp_product_categoryerp_px_cat_g1v2Convert the maintenance flag to boolean.
Gold model
  • dim_customers — CRM customers enriched with ERP demographics and location, with a ROW_NUMBER surrogate key. Gender comes from the CRM, falling back to the ERP when missing.
  • dim_products — CRM products joined to ERP categories, with a surrogate product_key.
  • fact_sales — sales lines joined to both dimensions, carrying order, ship and due dates plus sales amount, quantity and price.

A typical question it answers — revenue by country and product line:

SELECT c.country,
       p.product_line,
       SUM(f.sales_amount) AS total_sales
FROM   datalakehouse.gold.fact_sales    f
JOIN   datalakehouse.gold.dim_customers c ON f.customer_key = c.customer_key
JOIN   datalakehouse.gold.dim_products  p ON f.product_key  = p.product_key
GROUP  BY c.country, p.product_line
ORDER  BY total_sales DESC;
Running as a job

The four notebooks map directly onto a Databricks Job with four dependent tasks: init (once) → ingest (Bronze) → transform (Silver) → model (Gold). Each layer only starts when the previous one succeeds.
