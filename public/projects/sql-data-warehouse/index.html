SQL Server Medallion Data Warehouse

An end-to-end data warehouse in Microsoft SQL Server that merges CRM and ERP exports into a star schema ready for analytics.

The problem

Sales questions — who buys what, where, and how often — need customers, products and transactions in one place. Here they lived in two systems: a CRM (customer info, product info, sales details) and an ERP (customer demographics, locations, product categories). The two used different key formats, different codes for the same values, and had the usual quality issues: duplicates, stray whitespace, dates stored as integers and impossible birth dates.

The goal was a single warehouse where an analyst can join a clean fact table to clean dimensions and trust the result.

Architecture

One DataWarehouse database with three schemas, one per Medallion layer:

  • Bronze — raw ingestion. Each source CSV is loaded as-is into its own table with BULK INSERT, wrapped in the stored procedure bronze.load_bronze.
  • Silver — cleaning and standardization. silver.load_silver deduplicates, trims, casts types, validates values and standardizes codes across both systems.
  • Gold — analytical model. Views expose a star schema: gold.dim_customers, gold.dim_products (SCD Type 1 catalog) and gold.fact_sales, ready for any BI tool.

Transformations & lineage

Every source file is traceable to the Gold object it feeds:

Source fileGold objectKey transformations
cust_info.csvdim_customersKeep the latest record per customer by create date; trim names; map marital status (S/M → Single/Married) and gender (M/F → Male/Female).
LOC_A101.csvdim_customersRemove hyphens from keys; normalize country codes (DE → Germany, US → United States).
CUST_AZ12.csvdim_customersStrip the NAS prefix from IDs; invalidate future birth dates; standardize gender.
prd_info.csvdim_productsSplit the compound product key to extract the category ID; map product lines; derive end dates with LEAD().
PX_CAT_G1V2.csvdim_productsTrim whitespace; map categories and maintenance flags.
sales_details.csvfact_salesCast integer dates to DATE; check and repair pricing so that Sales = Quantity × Price.

Data quality

Quality checks live in the repository as SQL scripts, run after each load:

  • tests/quality_checks_silver.sql — formatting, trimming and date-normalization rules.
  • tests/quality_checks_gold.sql — key uniqueness, foreign-key mappings between the fact and dimensions, and overall model integrity.

Scripts are idempotent (they check OBJECT_ID before creating objects), and the repo includes a data_catalog.md and naming_conventions.md so the model is documented, not just built.

Running it

After creating the database, schemas and tables, the whole pipeline is two calls:

-- Load raw CSVs into Bronze
EXEC bronze.load_bronze;

-- Clean, standardize and load Silver
EXEC silver.load_silver;

The Gold layer is made of views, so it is always current with Silver.
